# AI 怎么从试用走到业务流程：验效果、算成本、管执行

**从「有人在用」到「值得接入生产」，中间差的是可验收的结果、算得清的成本和受控的执行权。** 这一章不排模型名次，而是用一个虚构的售后流程说明：哪些环节值得先做，什么证据能支持扩张，以及什么时候应该先停在「建议」而不是「执行」。

- [**先验效果**](#_1)：用可比任务设验收基线，不拿企业采用率代替效果。
- [**再算每个合格结果的成本**](#_2)：模型、等待、复核和返工都要计入。
- [**最后给执行权**](#_3)：从只读和草稿开始，扩大授权前先演练超时与接管。

> 公开资料核对于 2026 年 11 月。报告、实验和规范的日期分别注明；示例为教学构造，不代表任何实际公司流程。

## 采用率说明有人用，不能说明用在哪都赚钱

在 [OECD 2026 年 1 月发布的统计](https://www.oecd.org/en/about/news/announcements/2026/01/ai-use-by-individuals-surges-across-the-oecd-as-adoption-by-firms-continues-to-expand.html)中，有可用数据的 OECD 国家里，报告使用 AI 的企业占比从 2023 年的 **8.7%**、2024 年的 **14.2%** 上升到 2025 年的 **20.2%**。这不是全球企业占比，也不是生成式 AI 在生产流程中的部署率。

阅读采用数据时先区分：**试用过、某个职能在用、嵌入生产、产生净收益**，这四件事不是同一个指标。一个人用模型起草邮件，不能说明同一个系统已具备独立处理退款的能力。

效率也要回到具体任务。[METR 的编码实验及跟进](06-llm-capability-boundaries.md#c7c)说明，即使在同一个职业里，任务、工具和计时方式变化也会改变结果。试点不能照搬外部实验的提速数字。

客服有另一种现场证据。[《Generative AI at Work》期刊版](https://academic.oup.com/qje/article/140/2/889/7990658)研究了一家企业分批向 5,172 名客服人员部署辅助工具的过程。获得辅助后，**每小时成功解决的问题平均增加约 15%**，收益主要集中在经验较少或原来表现较弱的人群。工具给出建议，客服人员仍负责对话；这不是自动客服能独立处理退款的证据，也不是企业投资回报率。两个行业的案例不是在比谁更适合 AI，而是在说明：**任务、用户和介入方式变了，收益就要重测。**

真实试点可以对同类任务随机分流，或在条件相近的任务上做配对比较。提前约定什么算验收通过，以及哪类错误即使比例低也不能接受。不要把采纳、速度和质量混成一个指标：少花时间却增加返工，不等于有净收益。

## 按经过验收的任务算成本，不按便宜的一次调用算

模型推理确实可能更便宜。[Epoch AI 2026 年 9 月的分析](https://epoch.ai/publications/the-plunging-price-of-thought)用 GPQA Diamond 科学问答作对照：达到 **81.25% 原始准确率**时，观测到的最低推理成本从约 **0.30 美元/题**降到约 **0.0004 美元/题**。分母是尝试回答的题，不是答对的题；这反映特定基准和模型选择下的成本，不是客服、研发等真实流程能省多少钱。

| 观察量 | 怎么记 | 为什么单看平均值不够 |
| --- | --- | --- |
| 任务结果 | 按已验收、拒绝、转人工、超时等终态计数 | 流畅的答复可能没改动任何实际状态，也可能做了不该做的事 |
| 一次尝试的全成本 | 模型、检索和工具、等待、人工复核、重试、返工 | 低单价模型可能因失败或多轮查询而更贵 |
| 每个合格结果的成本 | 同一试点期内所有尝试的总成本 ÷ 合格交付数，另报合格率 | 如果合格数为零，比率无定义；如果只留下简单任务，数值也会失真 |
| 尾部影响 | 超时比例、耗时高分位、关键错误和有害副作用 | 少数严重错误不能用大量简单任务的平均成绩抵消 |

例如，虚构试点中 100 个同类工单花了 600 元（含重试及复核）并交付 75 个合格结果，成本是 **8 元/合格结果**，合格率 75%。不要拿这个数字直接和只统计模型账单的实验比较。涉及路由、预算和计量的工程细节见[《成本控制与模型路由》](../p3-agent-internals/17-cost-and-routing.md)，评委与回归集见[《Agent 评测实践指南》](../p3-agent-internals/14-agent-eval-guide.md)。

## 能提出建议和有权执行是两个上线阶段

以虚构售后助手为例，让系统按风险逐步拿到权限，而不是第一天就自动改真实订单。

```d2
direction: down
replay: "离线回放\n不连写工具"
draft: "生产只读 / 草稿\n由人复核"
approval: "批准后执行\n绑定具体订单和金额"
auto: "窄范围自动执行\n预设上限与停机条件"
replay -> draft: 离线验收通过
draft -> approval: 核清身份与授权
approval -> auto: 通过恢复演练与放量检查
```

**读图：** 箭头是放量条件，不是上线必经路径。只读能带来收益时，可以一直停在草稿阶段。

| 阶段 | 允许做什么 | 放量前看什么 |
| --- | --- | --- |
| 离线回放 | 对历史任务的脱敏副本给出建议，不接写工具 | 能查到正确政策、不过度引用过期条款、知道何时转人工 |
| 生产只读或草稿 | 读取本人有权查看的订单，生成解释或待审批方案 | 草稿通过率、人工修改量、越权尝试、隐私暴露、审阅是否真省时 |
| 人工批准后执行 | 审批指定订单和金额；执行器核验审批人与最新状态，再发起操作 | 未批不执行，重试不重复，撤销或补偿路径能跑通 |
| 对窄范围自动执行 | 仅在预定义类别、金额、租户与调用上限内执行 | 阈值外默认拒绝，审计可追溯，有停机开关和回退程序 |

**一次审批应绑定到具体动作，不是给 Agent 一张通行证。** 读订单、起草方案、申请批准、更新订单应分成不同权限。外部页面或用户上传的材料里出现的指令只是数据，不能改变授权。跨工具或跨 Agent 的接口便于连接系统，但不能代替服务端鉴权、幂等、审计和人工升级。可对照[《Agent 运行线路图》](01-agent-runtime-map.md)与[《Claude Code Harness 搭建指南》](07-claude-code-harness-guide.md)理解执行边界。

[NIST AI 风险管理框架](https://www.nist.gov/itl/ai-risk-management-framework)的 Govern、Map、Measure、Manage 可用作自愿参考：明确谁负责和应用场景，测量失败，定义如何监控与干预。它是风险管理框架，不是对某个项目通过合规审查的证明。

### 退款请求超时，先核实结果，不要重新发一笔 { #refund-timeout }

虚构案例：网关已派发退款，但等待回执超时。这只能证明**调用方没收到结果**，不能证明退款没发生。用原操作编号向退款服务核对：

| 核对结果 | 怎么处理 |
| --- | --- |
| 已完成 | 记录实际回执，不再发起退款。 |
| 仍在处理 | 保留「处理中」状态；按业务规则等待或转人工。 |
| 确认未执行 | 仅在授权仍有效、接口支持去重且重试预算允许时，带原操作标识重试。 |
| 无法确认 | 停止自动写入并转人工，交接订单、审批和操作记录；不要报告成功或失败。 |

这个用例应该在放量前演练一次。检查的不只是「能不能退」，还有超时时能不能说明真实状态、避免重复操作。

### 试点结束时做的决定 { #_4 }

- **扩张**：在可比任务上，质量与高风险错误达到事前口径，净收益为正，且执行可暂停、可追溯。
- **保留辅助模式**：草稿有用，但验收成本、权限或不可逆后果还没治理好。
- **缩小范围或停止**：收益依赖挑简单任务、漏算人工、或者一次严重错误就能抵消平均收益。先修边界，不急着换更大的模型。
