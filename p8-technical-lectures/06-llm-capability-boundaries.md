# 大模型的能力边界：论文、评测与现实各能说明什么？

**理论结果、模型评测和生产试点回答的是三个不同的问题。** 理论说明特定模型在给定前提下的限制；评测说明系统在一组任务上的表现；实际试点才会回答，在目标任务、风险和验收成本下，哪些步骤值得交给 Agent。

## 理论限制有前提，不能直接套到带工具的 Agent

| 边界 | 该问什么 | 不能直接推出什么 |
| --- | --- | --- |
| 表达力 | 对深度、精度和推理步数做了什么假设？ | 一个数学模型的限制，不等于所有实际系统都做不了这类任务。 |
| 信息 | 所需事实能从输入或可信来源获得吗？ | 无资料时答得流畅不代表正确；这也不意味着有证据可查时仍无法改善。 |
| 泛化 | 测过熟悉题型，还是改变条件以后的新任务？ | 在常见题型答得对，不代表改变条件或规模仍然可靠。 |

例如，关于固定推理步数的结果，不能直接套到能调用计算器、读取文档和反复检查结果的系统上。反过来，接了工具也不代表绕过了所有限制：系统还得选对工具、取得可信结果，并据此更新判断。

## 基准成绩不能直接换算成真实提效

| 证据 | 能回答 | 不能单独回答 |
| --- | --- | --- |
| 公开任务基准 | 在规定任务集和判卷规则下，系统能完成多少任务？ | 换成自己的项目能节约多少时间？ |
| 有对照的实际任务实验 | 在给定参与者、任务和工具条件下，净耗时或质量是否变化？ | 新模型、新团队和其他工作能否得到同样结果？ |
| 目标工作流试点 | 算上等待、复核和返工，净收益是多少？ | 整个岗位或行业会不会被替代？ |

例如，METR 的任务时长指标以**人类完成任务所需的时间**为尺度，估计系统在特定任务集上达到某个成功率时对应的任务长度。它不是 Agent 能无人值守连续运行多久的计时器。

## 能不能交给 Agent，先看验收是否可靠

以一个虚构项目为例：修一条输入校验，行为可以用反例说清，改动可以用测试检查，失败还能回滚。这适合让 Agent 先产出改动，再由测试和人复核。换成「决定对谁执行不可逆操作」，模型生成看似合理的建议，也不等于系统拿到了执行授权。

试点前问三件事：**目标能写清吗？错误能以合理成本测出来吗？漏检时能否限制后果或回滚？** 如果其中一项没答案，先让 Agent 产出建议或草稿，不要默认交出执行权。历史背景见 [LLM 发展过程中的质疑与成长](04-llm-development.md)。
