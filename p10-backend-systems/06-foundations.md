# 网络与运行时：从请求超时反推连接、线程和 I/O

> 本章为独立原创；备考范围见[后端面试导读](00-guide.md)。

**基础题先用一句话说明机制，再用一次故障说明边界。** 能区分「TCP 没连上」「连接已建但没收到响应」「业务已经提交但客户端不知道」，比背一长串协议名更有用。

## P0：TCP 确认了字节，不确认业务成功

| 45 秒首问 | 能过关的回答 | 故障追问 |
|---|---|---|
| 一个 HTTPS 请求经过什么？ | 解析地址，新连接走相应的传输与安全握手，再发 HTTP 请求；缓存与连接复用可跳过部分步骤。HTTP/1.1 和 HTTP/2 的常见 HTTPS 路径基于 TCP+TLS，HTTP/3 基于 QUIC。 | TTFB 变长时，分开看 DNS、建立连接、TLS、连接池等待和服务端处理；别把 TTFB 全算到数据库。 |
| TCP 为什么三次握手？ | 双方交换初始序列号并确认对端收到；连接建立后，TCP 给应用可靠、有序的字节流，不保留应用消息边界。 | TCP ACK 不说明订单已提交；HTTP 读超时以后，用同一幂等键查或重试，不默认原操作失败。 |
| HTTP/1.1、HTTP/2 与 HTTP/3 的并发差别？ | HTTP/2 在一条连接上多路复用，但同一 TCP 连接丢包可拖住多个流的交付；HTTP/3 用 QUIC 独立交付各流的数据，共享连接资源时仍会互相影响。 | 看到多个请求一起慢，先区分传输层丢包、连接级容量与服务端整体过载。 |

## P0：I/O 多路复用解决等待，不解决计算和资源饱和

| 45 秒首问 | 能过关的回答 | 故障追问 |
|---|---|---|
| 进程、线程、并发、并行怎么分？ | 进程通常拥有独立地址空间；同一进程的线程共享地址空间，各自有执行上下文。并发是任务交错推进，并行是同时执行。 | 线程全在等待下游，就算 CPU 不高也可能没有余量；看活跃线程、队列、拒绝率和等待时间。 |
| `epoll` 做什么？事件循环为什么还会卡？ | Linux `epoll` 报告关注的文件描述符上的就绪事件，本身不执行应用读写；事件循环仍需运行用户代码，长 CPU 任务会延后其他回调。 | 先量事件循环延迟，并拆 CPU 热点、工作线程池及下游等待；不能只凭「异步」断言不阻塞。 |
| 线程池越大越好吗？ | CPU 密集任务不能靠线程数凭空增加算力；I/O 密集任务的并发上限仍受下游和内存约束。 | 先限制在途与队列，观察池等待和下游饱和度；用[稳定性专题](01-traffic.md)选择拒绝、降级或隔离。 |

## 自测：不许用「先扩容」跳过定位

1. 网关看到 504，应用日志却在 2 秒后记录订单提交。该怎么解释、怎么阻止建两单？

    <details><summary>自检</summary>

    网关等上游响应超时，不代表应用取消或数据库回滚。用 Trace 和订单键对齐时间线；通过持久化幂等键、唯一约束及同一事务记录请求结果，安全处理结果未知的重试。

    </details>

2. 应用 CPU 不高，P99 翻倍，线程池活动数打满。拿什么数据区分下游 I/O 等待和 CPU 热点？

    <details><summary>自检</summary>

    看线程采样的运行／等待位置、池队列等待、下游各 span 与主机逐核 CPU。如果是事件循环，还要看事件循环延迟与回调耗时。先指出能推翻自己猜测的一个信号。

    </details>
