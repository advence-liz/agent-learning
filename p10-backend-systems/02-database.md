# 数据库：先缩小扫描和锁范围，再谈读写分离与分片

> 本章为独立原创；备考范围见[后端面试导读](00-guide.md)。

**SQL 慢、事务冲突和数据库容量不足是三道不同的题。先用证据分开，再讨论索引、隔离与扩容。**

## P0：执行计划比背「索引失效」口诀更有用

面试官给你一张 `orders` 表：按 `user_id` 查最新 20 条，翻到第 5,000 页开始变慢。先看真实 SQL 和数据分布，比较执行计划的实际行数、扫描、排序、耗时；再看锁等待和连接池占用。以 PostgreSQL 为例，`EXPLAIN` 是计划与估计，`EXPLAIN ANALYZE` 真会执行语句，不能把写语句随手拿去线上跑。

**首答：** 用 `(user_id, created_at DESC, id DESC)` 作为这条查询的候选索引，`id` 打破时间戳并列。深 `OFFSET` 仍要跳过前面的记录；要连续翻页，可以把上一页最后一条的 `(created_at, id)` 当游标。下例假设两列非空、排序键稳定，第一页省略游标条件：

```sql
SELECT id, created_at, status
FROM orders
WHERE user_id = $1 AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**追问：** 游标不支持随意跳到指定页，也不自动提供跨请求的快照一致性；适合连续列表。别保证优化器一定走索引：要拿真实选择性、扫描行数、回表和排序量验证，还要算索引增加的写入和存储成本。

## P0：超卖约束应由数据库写入条件兜底

**首问：两个请求同时扣最后一件库存怎么办？** 单库内以原子条件更新 `UPDATE stock SET qty = qty - 1 WHERE sku = ... AND qty > 0`，检查影响行数，并把建单放到同一事务；用唯一约束防重复下单。不要用「先查 qty，再无条件减」当并发保护。

**追问：选择什么隔离级别？** 先说数据库与业务不变量：此例用行上的原子谓词保护不超卖；跨多行不变量要另讨论锁范围、可串行化事务及冲突重试。隔离级别不能替代幂等键。区分慢查询、锁等待、死锁，避免用拉长超时统一处理。

## P0：快照读回答「看见什么」，锁与约束回答「能不能改」

**首问：同一个事务读两次，能看见别人在中间提交的更新吗？** 先限定引擎和读法。以 MySQL InnoDB 普通一致性读为例，`READ COMMITTED` 每次一致性读取新快照；`REPEATABLE READ` 的一致性读复用事务内首次一致性读建立的快照（也能看到本事务自己的修改）。MVCC 用历史版本支持按快照读取，不是给每个事务复制整张表。

**追问：那为什么更新时还能等锁？** 普通快照读不是 `SELECT … FOR UPDATE`，也不是 `UPDATE`。写入必须和并发修改协调，不能拿旧快照下的 `qty` 当更新依据。追 B+ 树时先说明它为什么适合有序范围扫描，再用本章的分页查询讲联合索引和实际扫描，不要拿「走索引」等同于「快」。

依据：[MySQL 8.4：Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

## P1：副本扩读，分片扩单节点容量，但都不替代 SQL 优化

| 方案 | 什么证据才考虑 | 必接的追问 |
|---|---|---|
| 读写分离 | 优化后仍是读侧吞吐占主导，可容忍部分读旧 | 下单成功后立即查可能撞上复制延迟；关键读走主库，历史列表按业务容忍度走副本，监控复制延迟与主库容量。 |
| 水平分片 | 已确认单节点写入／存储容量不可接受 | 分片键要契合主要查询。按用户分片利于查订单，却不解决共享 SKU 热点；跨分片聚合、事务与扩容迁移都更难。 |
| 冷热分离 | 所需访问时效和保留周期有显著冷热差异 | 双读窗口或增量同步、校验、切换条件与回滚如何安排？这是 P2，不先背迁移实现。 |

## 练习：用并发时序和读路由把边界讲出来

1. 两个订单时间戳相同，只传 `created_at` 作游标会怎样？

    <details><summary>自检</summary>

    使用严格小于时可能跳过同一时间戳但还没返回的记录。把唯一 `id` 纳入排序和游标，仍需说明并发写入时不保证跨页快照。

    </details>

2. 下单返回成功，但有 2% 用户在详情页看到不存在。你怎么证伪「写没有成功」？

    <details><summary>自检</summary>

    用同一订单 ID 比对写提交记录、详情读路由、主库和副本状态，观察延迟分布；若确认为读己之写问题，先把该关键读路由到主库，再测主库余量。

    </details>
