# 后端面试导读：先练核心追问，再补组件细节

> **这条路线面向有工作经验的后端社招：先准备两段拿得出证据的真实项目，再补会被追问的基础，最后做限时设计。** 不把校招题单当社招数据，也不假设社招只问项目。

1. **项目深挖：先答「你做了什么，怎么证明有效」。** 准备一段选型／交付和一段故障／性能复盘；只有一段项目，也可以从两个决策切入。
2. **基础与故障：用 45 秒答机制，用 3 分钟接变体。** 从[网络与运行时](06-foundations.md)、[数据库](02-database.md)、[缓存](03-cache.md)和[消息队列](04-queues.md)查漏，再用[入口与稳定性](01-traffic.md)把证据、缓解和验证串起来。
3. **系统设计：用 25 分钟交付最小方案。** 做完[订单系统](05-system-design.md)，再换成异步任务平台。时间是练习目标，不是公司面试时长。

## 两天先练真实项目和 P0，再按目标岗位补课

| 主题 | P0：先开口答 | P1：再接追问 | P2：JD 点名再补 |
|---|---|---|---|
| 项目深挖 | 个人职责、指标口径、选型与取舍、验证结果 | 替代方案、线上故障、迁移与回滚 | 按岗位能力范围准备跨团队或多地域案例 |
| 网络与运行时 | HTTP/TCP、超时语义、进程与线程、I/O 就绪与饱和 | 连接复用、线程池和事件循环排障 | TIME_WAIT、虚拟内存、具体语言运行时 |
| 数据库 | 执行计划、联合索引、事务隔离/MVCC、条件更新 | 深分页、读己之写、分片键与热点 | 冷热迁移、日志与存储引擎深入 |
| 缓存 | Cache-Aside、热点失效、旧值回填 | 过期与淘汰、缓存不可用的保护、持久化取舍 | Redis 集群迁移、特定锁协议 |
| 消息队列 | 消息怎么丢、为什么重、怎么幂等、怎么查积压 | Outbox、分区顺序、毒消息与重放 | 只挑 JD 点名的一个 Broker 深挖 |
| 稳定性 | P99 排查、超时预算、重试放大、限流和背压 | CDN 回源、四／七层负载均衡、连接排空 | 多地域调度与容灾 |
| 系统设计 | 范围、接口与不变量、必要算量、最小方案 | 失效场景、指标与回滚 | 多活、跨地域一致性、复杂迁移 |

- **只剩 2 天**：第 1 天写两张项目卡，每张录一段 90 秒首答和两条追问；沿自己用过的 SQL、缓存或队列补一个失败场景，再抽查 HTTP 与并发基础。第 2 天限时做一题，选一次过载或一致性故障深入，并留时间做目标岗位的编码练习。
- **有 1 周**：前两天照做；第 3–5 天补薄弱基础、练一次线上排障；第 6 天按 JD 补语言运行时和指定组件；第 7 天模拟一轮项目追问和一轮设计，先记录答不出的问题，不按阅读进度验收。
- **按岗位调权重**：业务后端先练数据正确性与交付；平台／基础设施先练容量、降级和故障恢复；Agent 应用后端用异步任务题练幂等、取消与任务隔离，模型和工具机制走 [Agent 研发面试](../p7-interview/01-interview-landscape.md)。编码和算法在独立路线训练，不从社招准备中删掉。

## 项目卡要经得起「为什么是你、为什么是这个方案」

| 写四行 | 面试官可以怎么追 |
|---|---|
| 业务目标、约束与你负责的边界 | 哪一部分是你决定、实现或验证的？哪些是团队做的？ |
| 症状与原始证据 | 指标怎么定义？流量与时间窗口是否可比？如果没测过，手头到底有什么证据？ |
| 选项、否决理由与失败边界 | 为什么没选另一种方案？依赖不稳定时先保谁？ |
| 上线验证和改进 | 怎么灰度、怎么回滚？重做会改什么？ |

没有真实故障就讲一次失败的验证或取舍，说明是本地实验、压测还是真实线上经历；不要把课程示例写成自己的生产数据。

## 同一条订单链路会暴露不同层的瓶颈

```d2
direction: down
client: 客户端
api: 入口与订单 API
db: 数据库（订单事实来源）
cache: 缓存（可过期的查询结果）
queue: 消息队列
worker: 通知 Worker
client -> api: 查单／下单
api -> cache: 查询允许短暂读旧的数据
api -> db: 写入订单和 Outbox／必要时回源
db -> queue: Relay 转发已提交的 Outbox
queue -> worker: 投递通知事件
```

读图时只问三个问题：**哪里可能排队？哪里承诺事实？哪个副作用可能重复？** 图是本路线的练习案例，不是所有系统都要一上来部署这些组件。

## 能回答一次变体，才算真正过关

首答按 **约束 → 证据 → 最小方案 → 失败边界 → 验证指标**。先脱稿，再展开答案对照。比如答「加 Redis」，还得讲清什么允许读旧、回源峰值怎么限制，以及哪个观测值能证明 DB 压力真的下降。

**起点自测：** 上线后订单 API 的 P99 翻倍，平均值几乎没变。你先查哪三处？拿到什么证据才会去改 SQL？

<details><summary>自检</summary>

先按端点／版本确认真实延迟和错误率；看慢 Trace 的耗时跨度；对照连接池等待与 SQL 执行耗时。只有证据指向查询本身，再看慢 SQL、执行计划和锁等待；连接池排队不等于 SQL 扫描太多。
