# 消息队列：允许重复投递，但不能重复产生业务效果

> 本章为独立原创；备考范围见[后端面试导读](00-guide.md)。

**把可延迟的副作用移出下单请求；面试时沿着提交、发布、投递、消费四个边界讲清哪里会丢、哪里会重。**

## P0：确认不是业务完成，先画出故障发生的位置

```d2
direction: down
api: 订单 API
db: 订单库（订单＋Outbox）
relay: 转发进程
broker: Broker
worker: 通知 Worker
api -> db: 同一事务写入
relay -> db: 取已提交事件
relay -> broker: 发布，等待 Broker 确认
broker -> worker: 投递，失败可能再投
worker -> broker: 处理完成后确认／提交位点
```

| 故障 | 会发生什么 | 答题要点 |
|---|---|---|
| 订单提交了，进程还没发消息就崩溃 | 「先写库再发消息」留下双写缺口 | 订单与 Outbox 事件同一事务提交；独立 Relay 扫描或订阅提交记录再发布。监控未转发事件的最老年龄。 |
| Broker 收到了，但发布方没收到确认 | 重发可能重复 | 使用稳定 `event_id`，不能每次重试生成新 ID；确认的耐久性取决于 Broker 与副本配置。 |
| 消费业务已提交，确认失败 | 同一消息可能再次投递 | 去重记录与本地副作用同事务提交，用唯一约束仲裁；先提交业务再确认。 |
| 外部通知已发出，但本地没记成功 | 下次发送可能重复 | 优先用外部 API 的幂等键；否则要承认结果不确定，靠查询、对账或补偿，不能拿本地唯一键承诺端到端恰好一次。 |

对下单 API 同理：幂等键要按业务主体与操作域隔离，同键不同请求体应拒绝，重试要拿到已提交结果；不要用「先查没写过」代替唯一约束。**Outbox 补的是数据库到消息发布的缺口，不消除转发重复。**

## P0/P1：消费积压时先查下游，不一定该加 Worker

**追问：10 分钟后能清空吗？** 如果在有效处理速率稳定、忽略重试等因素时，积压清空时间约为 `积压量 ÷（成功消费速率 − 新增速率）`；差值非正就清不掉。先看生产速率、完成速率、最老消息年龄、分区偏斜、重试率和下游耗时。只有在下游有余量、分区或工作拆分允许时才加并发；否则先限流、隔离失败消息并恢复下游。

**追问：同一订单要顺序，所有订单要不要顺序？** 先问是否只要求同一订单内有序。以 Kafka 为例，可让同一订单进入同一分区；分区内读取有顺序，但消费者内部并发、失败后的重试与独立重放仍会改变业务完成顺序。全局排序成本更高，别默认承诺。中高级面试可继续追分区热点、毒消息是阻塞还是跳过、死信如何安全重放。

## 练习：在故障点之后还能解释数据怎么恢复

1. 当前积压 90,000 条，每秒新增 250 条，成功处理 400 条。多久清空？什么情况下估算不成立？

    <details><summary>自检</summary>

    约 600 秒。下游吞吐变化、失败重试占用资源或分区偏斜会改变有效消费速率；还要对照最老消息的业务时效。

    </details>

2. 账单消费者提交了本地事务，ACK 前进程崩溃，再次启动时如何验证没有重复入账？

    <details><summary>自检</summary>

    让同一个事件 ID 重投，验证业务账目仅新增一次、去重记录与账目在同一事务，消费者成功确认。如果涉及外部扣款，另验证对方支持的幂等键与重复提交语义。

    </details>
