# 请求入口与稳定性：请求变慢时，先找到在哪排队

> 本章为独立原创；备考范围见[后端面试导读](00-guide.md)。

**P99 变差时，不要先加实例或拉长超时。先找耗时落在入口、应用、连接池还是下游；再用有限等待和并发预算阻止故障扩散。**

## P0：平均值看起来正常，不代表用户都正常

```d2
direction: down
edge: 网关／负载均衡
app: 应用实例
pool: 数据库连接池
db: 数据库
edge -> app: 路由请求（看入口等待）
app -> pool: 获取连接（看等待与超时）
pool -> db: 执行 SQL（看查询与锁等待）
```

端到端延迟包含等待，不等于服务实际执行时间；不能把各段的 P99 直接相加当成端到端 P99。P99 是延迟分布的尾部位置；QPS 数请求，TPS 数指定的业务事务，并发数是在途数量。流量总体稳定时，可以用「平均在途数 ≈ 到达速率 × 平均停留时间」做量级检查，不能拿 P99 代替平均值。

**面试首问：订单接口 P99 从 150 ms 涨到 900 ms，怎么排？** 先切端点、区域和版本，确认是全局还是局部；看请求量、延迟、错误与资源饱和度。抽慢 Trace，拆入口等待、应用处理、连接池等待和下游调用，再和发布或流量变化对齐。如果 SQL 耗时稳定但拿连接更慢，先看持有时间、并发占用和池等待，不盲目放大连接池。

**追问：下游变慢，为什么重试会让自己也挂？** 每一层各尝试 3 次（含首次），三层叠加最多可把一次上游调用变成 27 次末端尝试。只在选定层、剩余 deadline 内重试瞬时错误，用有上限的退避和抖动；有副作用的请求还需要幂等。客户端超时只表示没等到，不能假定服务端没提交。限流约束流入速率，并发上限和有界队列限制在途资源；过载时拒绝或降级非关键请求，而不是无限排队。

## P1：CDN 减少回源，负载均衡分流回源请求

| 面试问法 | 回答抓手 |
|---|---|
| CDN 和负载均衡有什么不同？ | CDN 命中边缘缓存时不用回源；负载均衡把仍需处理的流量分到健康实例。四层主要按传输层连接调度；七层可按 HTTP Host、路径等信息路由。 |
| 发布后 JS 404？ | 带内容指纹的静态资源可以长缓存；HTML 的缓存策略要考虑引用旧资源的窗口。先看缓存命中、回源流量、HTML 引用的指纹和旧资源还在不在。个性化响应不能误进共享缓存。 |
| 节点正在下线？ | 先停止分配新流量，给在途请求排空窗口；长连接要有退出／重连方案。健康检查通过，不等于有足够容量。 |

## 练习：用一个数字与一次排障证明你的选择

1. 2,000 req/s、平均停留 80 ms，对应多少平均在途请求？同样流量下变成 200 ms 呢？

    <details><summary>自检</summary>

    分别约 160 和 400。要算同一系统边界、同一统计窗口；流量正在快速堆积时只适合看量级。

    </details>

2. 只有一个租户突增，订单列表拖慢下单，你先做哪两件事？

    <details><summary>自检</summary>

    先按租户和路由定位占用，再隔离查询与写入的资源预算，给热点租户限制；看下单错误率、尾延迟、连接池等待是否恢复。别只看全站平均值。

    </details>
