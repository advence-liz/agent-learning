# 全栈与生产工程：把 Agent 交付成可靠产品

> 本章不对应原站文章，是知识库的补充章节（独立原创）

> **一句话结论**：全栈 Agent 岗不是「聊天框加模型 API」，而是同时交付可恢复的交互、可重入的任务、可隔离的数据和可度量的推理服务。面试要沿一次请求讲清状态、故障、权限与成本，而不是报技术栈。

## 「我会 React，也写过 Agent Loop，还差什么？」

差的是中间那条容易被 Demo 藏起来的链路：用户关了页面，任务还在跑；worker 重启，队列又投了一次；工具操作成功了，写成功状态前进程却崩了。

本章是**根据 JD 能力要求推导的备考题与设计示范，不是真实面经**。岗位深度在[备考地图](01-interview-landscape.md)，这里补四条边界：前后端事件契约、任务与副作用、推理资源、交付验收。设计示范不代表 mini Claude Code 已实现这些生产能力。

## 把故障题落到可运行的恢复、审批与取消实验

[Research Desk](../code/interview-node/README.md)提供本章设计的一个**本机教学实现**，不是宣称已经生产部署：

| 实验 | 命令（仓库根） | 看哪段代码与证据 |
|---|---|---|
| 跨进程接续 | `npm run example:4 --prefix code/interview-node` | [04-recovery.ts](../code/interview-node/examples/04-recovery.ts)启动两个进程，第二个从 SQLite 继续，不重复已提交的 search 轮次 |
| 审批与取消 | `npm run example:5 --prefix code/interview-node` | [05-approval-cancel.ts](../code/interview-node/examples/05-approval-cancel.ts)验证未审批无报告、重复审批一份、取消不能审批 |
| HTTP / SSE | `npm start --prefix code/interview-node` | [server.ts](../code/interview-node/src/server.ts)将任务与连接分离，按 seq 重放事件，不输出模型 token 流 |

[Store](../code/interview-node/src/store.ts)用事务原子 claim、owner token 和租约有效期约束提交；[Runtime](../code/interview-node/src/runtime.ts)每轮保存检查点、续租并传播取消。强杀后未提交的一轮可能重跑并再次计费；同库报告与终态原子提交，不等于外部发信、支付 exactly-once。

默认 fake 模型、教学身份、loopback 服务。共享 SQLite 文件验证本机多进程机制，**不是跨 pod 的共享存储方案**；没有浏览器 UI、生产鉴权和云运维。先把这些边界讲清，再回答后面的生产设计题。

## 先把「业务任务」与「连接」分开

```d2
direction: down
ui: "浏览器\n按 run_id 展示状态"
api: "API / BFF\n鉴权、配额、幂等接单"
state: "持久化任务与事件\n状态版本、检查点、事件序号"
queue: "有界任务队列\n重投、超时与取消"
worker: "Agent worker\n持租约、保存检查点"
model: "模型网关 / 推理服务\n限流、路由、token 预算"
tool: "工具执行边界\n再鉴权、幂等副作用"
ui -> api: "创建 / 取消任务"
api -> state: "事务写任务与待发布事件"
state -> queue: "outbox 发布，允许重复"
queue -> worker: "至少一次投递"
worker -> state: "版本化写状态与事件"
worker -> model: "推理\n超时与预算"
worker -> tool: "动作\n授权与幂等"
state -> ui: "经鉴权 API 订阅或重放事件"
```

读图：连接是观察任务的通道，不是任务本身；数据库到队列的 outbox 是一种可选设计，用来处理双写故障，不是要求所有系统照搬。

**面试开场先问约束**：同步问答还是长任务？峰值并发多少？是否有支付、发信等副作用？是否需要断线恢复？数据能否跨租户、跨区？没有这些前提，「选 SSE 还是 WebSocket」答不完整。

## 流式 UI 要恢复的是状态，不只是续上文字

**题 1：SSE、WebSocket、轮询怎么选？**

SSE 适合服务端向浏览器单向推送；客户端可以另发 HTTP 请求取消或审批。WebSocket 提供双向通道，但不自带持久化、业务重放或幂等。低频任务可以先用轮询。原生 EventSource 的方法、鉴权方式与 fetch 流读取不同，要按客户端和网关约束选，不能只说「SSE 更简单」。[1]

**题 2：流里收到半截 JSON，怎么办？**

先做协议分帧，再做业务解析。网络 chunk 不等于一个 SSE event，更不等于一段完整工具参数。用增量解码器处理跨 chunk 字符，缓存到协议边界；工具参数收齐且 schema 校验通过后再执行。UI 可以显示增量文本，但不能把尚未闭合的对象当成最终产物。[流式响应](../p2-agent-basics/09-streaming-response.md)讲基础读取，这里加的是业务恢复协议。

**题 3：刷新页面后如何恢复？**

设计一个自己的、非服务商特定的事件契约，例如：

```json
{"run_id":"run_demo","seq":42,"type":"tool.finished","payload":{"call_id":"call_demo","status":"ok"}}
```

- `run_id` 标识任务，`seq` 在单个任务内单调递增，`call_id` 标识工具动作；不要用文本片段或接收时间推测身份。
- 客户端保存最后应用的序号，重连时请求补发。服务端若保留窗口不足，返回含水位序号的快照，再接后续事件；快照和增量的切换必须无缝衔接。
- 重复事件去重；发现序号缺口就补拉，而不是静默跳过。终态及产物以服务端持久状态为准。
- 重放与快照接口同样要做租户与资源鉴权，不能凭猜到一个 run_id 就读取。

**题 4：用户点停止，为什么账单还在涨？**

浏览器 AbortController 只说明本地请求取消了，不保证服务器、worker、模型服务和外部工具已经停下。要有幂等取消接口、服务端取消标记、worker 检查点，以及向下游传播的取消信号 / 超时；已经完成的外部副作用可能不可撤销。

前端把「正在申请取消」和「已取消」分开显示。还要定义取消与成功同时发生时谁获胜，使用状态版本 / 条件更新收口，而不是两个回调最后谁到谁覆盖。

**题 5：React 里怎么防串会话和卡顿？**

按 `run_id/message_id/block_id` 归一化状态，使用 reducer 或等价状态机；异步回调携带任务身份，切会话后旧流不能继续往当前会话追加。批量合并高频增量，避免每个 token 全树渲染；长列表考虑虚拟化，富文本渲染防 XSS，文件预览与下载按权限隔离。测试乱序、重复、截断和切会话，而不只测试快乐路径。

前端基础还包括键盘焦点、状态播报、对比度与减少动态效果等可访问性（a11y）要求；流式内容不要每个 token 都触发读屏播报。这里列出验收边界，尚未提供完整可访问性测试工程。

## 任务可重试，不等于副作用可随便重做

**题 6：队列重复投递，如何防止两次退款？**

幂等至少分两层：创建任务的请求键，和每个外部动作的稳定操作键。同一个动作的重试必须复用同一个键；不能每重试一次就生成新 key。用唯一约束、动作账本记录 `pending/succeeded/unknown` 等状态，返回已知结果。[2]

最难的故障窗口是：**外部成功，内部未记账就崩溃**。若下游支持幂等键，重试查询 / 调用可取回结果；不支持时，需要对账、补偿或人工介入。单靠本地数据库事务和 Redis 锁，不能保证外部副作用 exactly-once。

**题 7：多个 worker 抢同一个任务，Redis 锁够吗？**

租约过期后旧 worker 可能还活着。任务领取要有到期租约、心跳和版本条件；必要时用单调递增的 fencing token，让资源端拒绝过期持有者写入。只有当被保护资源实际校验 token 时，它才有隔离作用。[3]

模型调用和工具动作都有 wall-clock 超时、并发上限与取消路径；限制租户 / 用户 / 全局并发，排队必须有界，满了快速拒绝或明确回压。不在一次数据库事务里持锁等几分钟模型回复。

**题 8：数据库和队列双写怎么处理？**

事务里同时写任务和 outbox，异步发布器把 outbox 送到队列；发布后、标记前崩溃仍会重发，所以消费者仍须幂等。检查点只记录可恢复的步骤，恢复时核实外部动作账本，不盲目从第一步重跑。[4]

数据库基础追问别躲：唯一索引保证什么，隔离级别防什么，乐观锁为何要检查受影响行数，分页和索引怎么验证。Redis 是缓存还是事实源、TTL 到期会怎样，也必须说清。

**题 9：多租户隔离放在哪？**

身份来自服务端验证的凭证，不能信任模型或客户端传来的 tenant_id。查询、向量召回、文件、缓存、事件重放、工具调用与日志都带授权边界；缓存键也要考虑权限与数据版本。检索时就过滤不可见文档，不是先召回跨租户内容再要求模型「不要说出来」。

工具是最后一道业务边界：模型想做，不代表当前用户能做。SSRF、命令注入、路径穿越、任意文件读取与提示词注入分别测试，见 [Agent 安全](../p3-agent-internals/15-agent-security.md)。

## 传统全栈基础不能被 Agent 名词替代

这些是自测题，答案给到判别点；若离开提示还答不完整，需要另做语言 / 后端基础练习，不代表本书已展开完整课程。

| 追问 | 至少要答到的边界 |
|---|---|
| Node 单线程为什么能处理多个 I/O，为什么一次同步大计算会卡住流？ | 事件循环与异步 I/O；CPU 密集工作应隔离到 worker / 进程；Promise 不会自动让同步计算并行 |
| Python async 能直接加速模型前处理吗？ | await 适合协作等待；阻塞调用会卡事件循环。线程、进程与设备计算按库行为选择；讨论 GIL 时说明运行时版本与构建，不能绝对化 |
| TypeScript 类型能防止工具参数错吗？ | 静态类型不会自动验证外部 JSON，API 与工具边界仍需运行时 schema、业务与权限校验 |
| Cookie / token、CORS、CSRF、XSS 分别解决什么？ | 身份与会话、浏览器跨源读取策略、借用登录态发请求、脚本注入不是同一个问题；CORS 不是服务端授权 |
| SQL 查询突然变慢，怎么找原因？ | 看执行计划、扫描行数、索引选择、锁等待和数据量；不能先加缓存掩盖错误访问模式 |
| 缓存过期、穿透、击穿与更新一致性怎么办？ | 先说源数据和可接受陈旧度，再谈 TTL、请求合并、预热与失效；私有结果不能跨租户缓存 |
| 链表 / 哈希 / 堆 / 图、LRU、限并发池，能现场写吗？ | 复杂度、边界与测试；Agent 岗仍可能有传统编程题。别把会调用 agent 当会手写 |
| 单测、契约测试和端到端测试分别发现什么？ | fake 能验证状态与错误处理，不证明服务商协议或真实模型效果；外部边界与真实质量另验 |

## 推理部署要说清吞吐、延迟与质量的交换

**题 10：vLLM 为什么适合服务多请求？**

PagedAttention 的核心是按块管理 KV cache，避免要求连续大块存储；continuous batching 在迭代边界调度活跃请求，减少等待整个静态 batch 的浪费。两者分别偏内存管理与调度，不是同一个概念。[6]

FlashAttention 通过分块等方法减少 attention 的高带宽内存读写，不等于把标准全注意力的计算量自动降成线性。量化减少存储 / 带宽开销，可能影响质量与算子表现；投机解码由草稿提出、目标验证，也取决于接受率和实现。[7]

**题 11：QPS 翻倍，直接扩 GPU 吗？**

先测排队、输入 / 输出长度、prefill / decode、缓存命中和各工具耗时。限制并发 token 预算、最大输出与请求长度；再评估 batch、量化、前缀缓存、路由、扩容。调 batch 提升吞吐可能损害交互尾延迟；GPU 热启动与模型加载也影响扩容时效。

缓存须同时满足内容相同与授权正确；不同模型、模板、租户或数据版本不能随意共用。张量并行拆层内运算，流水线并行按层拆；跨卡通信并不免费。这里只覆盖原理，**没有多 GPU 调优实验**。

**题 12：云 API 超时，切备用模型不就行了？**

设单次及整任务 deadline、有限重试、退避和抖动，区分可重试与不可重试错误，避免层层重试形成风暴。fallback 前确认工具 schema、上下文长度、消息协议、图片 / 思考内容、策略与数据区域是否兼容；工具已执行的动作不能随模型重试再执行一次。成本路由见 [成本控制与模型路由](../p3-agent-internals/17-cost-and-routing.md)。

## 交付证据要覆盖工程、模型与产品，而不只是一张截图

**题 13：你怎么证明这个 Agent 可以发布？**

| 层 | 至少提供的证据 | 常见漏项 |
|---|---|---|
| 工程 | 单测、契约测试、离线 fake 集成、故障注入、端到端流程 | 只 mock 成功，不测超时 / 重投 / 断线 |
| 模型 | 固定评测集、基线、切片、重复运行、人工校准 | 只看平均分，把 LLM 评委当真值 |
| 产品 | 任务完成、纠错成本、用户采纳 / 放弃，配安全与质量反向指标 | 转人工下降，但用户问题其实没解决 |
| 运行 | SLO、trace、p95、错误率、预算、告警、灰度与回滚 | 只部署代码，漏了 prompt / 模型 / 工具版本 |

评测数据须区分开发集、回归集与留出测试集；模型、提示词、工具与检索版本都随发布记录。监控日志脱敏，trace 不应成为新的敏感信息泄漏源。CI/CD、容器、密钥注入和回滚也是全栈岗位的工程基本功，不是让模型部署一次就算完成。

## 动手：用故障表验收一个长任务设计

不必先接真实模型。让离线 fake worker 按固定脚本发事件，在设计或测试里逐项注入以下故障；表里的结果是**验收目标，不是已跑结果**。

| 注入故障 | 期待观察到的行为 |
|---|---|
| 同一个创建请求发两次 | 同一幂等键只产生一个业务任务 |
| 收到 seq 8、8、10 | 8 只应用一次，缺 9 时补拉 / 取快照，不静默丢失 |
| 外部动作成功后 worker 崩溃 | 用稳定动作键恢复结果，或标 unknown 待对账，不盲目重做 |
| 用户取消与任务完成并发 | 状态版本确定唯一终态，取消响应解释最终结果 |
| 切换会话后旧流继续到达 | 不污染新会话 |
| 尝试订阅另一租户 run_id | 服务端拒绝，不返回快照或历史事件 |
| 队列满、下游持续 429 | 有界排队、限流或明确拒绝，无无限重试 |

你日常做的 React webapp 正好能作为素材：把加载态、重试按钮和权限判断串成后端真实状态，而不是只画一个会动的气泡。

回到开头：会 React 和循环是起点，交付要补齐跨进程、跨连接、跨租户的边界。回到主线：上下文决定模型能看到什么，产品和基础设施决定结果能否安全、可靠地落地。

## 常见坑

- **把连接当任务。** 页面断开就丢任务，或者误以为断流等于停止计费。
- **把锁当幂等。** 锁过期、进程崩溃和外部副作用窗口都还在。
- **只背 vLLM 名词。** 讲不出 KV cache、排队、并发 token 和尾延迟之间的关系。
- **把索引 / cache 的 tenant_id 当成可信输入。** 权限身份必须由服务端验证。
- **把设计表说成已实现。** 需要把目标转成测试和观测证据，才能写进简历。

## 练习

**1.** 为你熟悉的 webapp 画出「创建、运行、等待审批、取消、失败、完成」状态转移，说明每条边由谁确认。

<details><summary>提示</summary>

检查取消与完成竞争、重复审批、超时恢复；终态不能被晚到的 running 覆盖。先约定状态版本和条件更新，再决定前端按钮文案。

</details>

**2.** 设计“外部扣款成功，但本地记账前进程崩溃”的恢复测试，并说明下游不支持幂等键时怎么办。

<details><summary>提示</summary>

区分任务键与动作键；动作键跨重试保持稳定。有下游幂等或查询接口时恢复已知结果；没有时标记 unknown 并对账、补偿或转人工。仅加本地事务、重试或锁都不足以保证外部动作只发生一次。

</details>

**3.** 开放题：设计一个 45 分钟全栈 Agent take-home 的最小验收范围，你会舍弃什么？

<details><summary>提示</summary>

优先一条闭环：鉴权后的任务创建、fake 流式事件、刷新恢复、取消、工具幂等与少量失败测试。明确哪些只画设计而没实现；不要用几十个工具和多 agent 掩盖主链路不完整。

</details>
