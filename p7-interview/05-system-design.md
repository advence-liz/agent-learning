# 系统设计：把模型、Agent 与生产约束组合成方案

> 本章不对应原站文章，是知识库的补充章节（独立原创）

> **一句话结论**：系统设计不是罗列组件，而是从需求出发，在模型能力、Agent 控制流与生产约束之间做取舍，并明确评测与失败恢复。用同一套六步框架答题，每步都交代代价。

## 「单项都能答，为什么画完架构还是讲不下去？」

因为单项知识回答“能怎么做”，设计回答“在这个约束下为什么这样做”。先读完[模型](02-model-fundamentals.md)、[Agent](03-agent-mechanisms.md)与[生产工程](04-production-engineering.md)，再练把它们组合起来；不用再刷一套重复的概念题。

下面题目结合公开面经线索和教学设计，不保证特定公司实际问过。L2 表示组合基础能力，L3 表示需要更多约束与取舍，不对应确定面试轮次。

## 先把一个小系统跑通，再解释每一层为什么存在

配套 [Research Desk 完整实战](../code/interview-node/README.md)把“本地知识库研究 → 引用草稿 → 人工审批 → 保存报告”做成可运行闭环。先 `npm run demo --prefix code/interview-node` 看结果，再读 [HTTP 入口](../code/interview-node/src/server.ts)、[任务与事务](../code/interview-node/src/store.ts)、[单轮循环](../code/interview-node/src/agent.ts)。

用下面三条反问检验自己是否真的能设计，而不只是会画框：

- **删掉模型到审批之间的边界会怎样？** 模型将可能直接触发副作用；当前工具只能提交草稿。
- **删掉 owner 与租约的提交条件会怎样？** 旧 worker 的晚到响应可能覆盖取消或接管后的状态。
- **把 SQLite 换成 PostgreSQL 要保留什么？** 幂等键、原子 claim、并发上限、fencing、事件序号与报告事务，而不只是换连接串。

它是单 Agent、内置教学文档与本机数据库，不含多 Agent、向量摄取、浏览器 UI 或模型训练。下面的大系统题仍需补容量、质量和生产约束，不能把教学实现换个名字就说成企业平台。

## 系统设计的六步框架

系统设计题没有标准答案，面试官看的是你怎么拆问题、怎么取舍。用下面这六步答，至少不会漏掉大块：

```d2
direction: down
s1: "1 澄清需求\n用户是谁 · 哪些动作有副作用 · 怎样算做对"
s2: "2 Workflow 还是 Agent\n哪段路径固定 · 哪段交给模型"
s3: "3 循环和工具\n工具清单 · 权限分级 · 停止条件"
s4: "4 上下文和状态\n检索 · 压缩 · 记忆 · 状态外置 · 幂等"
s5: "5 安全\n致命三要素 · 沙箱 · 凭证"
s6: "6 评测和观测\n回归集 · 在线评委 · trace · 灰度"
s1 -> s2 -> s3 -> s4 -> s5 -> s6
```

每一步讲完，都补一句代价。比如第 4 步说「用子 agent 隔离上下文」，就接着说明额外模型调用、摘要损失与协调成本，以及哪些任务能独立执行。面试官的追问，大多是在问你没主动讲的代价。

## 示范一：设计一个 Coding Agent

下面是一段按六步展开的回答，大约十分钟。

**1. 澄清需求。** 我先确认三件事：它在用户本机跑还是在云端跑；能不能直接改代码、执行命令；交付物是一个 PR 还是直接合入。假设答案是：云端运行，可以改代码、跑测试，最后提 PR，由人审核合入。「做对」至少要求既有测试和独立验收用例通过、改动范围合理且不越权；仅让模型自己写的测试通过不够。

**2. Workflow 还是 Agent。** 主体用 agent，因为读哪些文件、改几处、要不要再跑一遍测试，没法提前写死。但两头用固定流程：开头固定执行「拉代码、装依赖、跑一遍现有测试」，结尾固定执行「跑测试、lint、提 PR」。中间才交给模型。

**3. 循环和工具。** 工具尽量少而通用：读文件、按字符串替换编辑文件、执行 shell、搜索代码。这里选通用工具，是为了减少接口种类并支持组合；是否比专用工具可靠，要在目标模型与任务集上验证，不能假定所有模型的训练覆盖相同。权限分三级：读文件和搜索自动放行；改文件放在沙箱的工作区里随意改；执行命令按白名单放行，联网的命令需要单独授权。停止条件：模型不再调用工具，或者撞上步数和时间上限；撞上限时让它总结做到了哪一步。

**4. 上下文和状态。** 大仓库不做向量索引，让 agent 用 grep 和 glob 按需查找，这样不会遇到索引过期的问题；项目约定放在仓库根目录的说明文件里，每次预先加载。长任务开启压缩，保留最近几轮原文和最近读过的文件。保留尾部要先处理 thinking 块，否则会失效，见 [compact](../p4-mini-cc/14-compact.md)。代码产物可以靠 git 检查点恢复，但任务、工具动作与外部副作用还要有持久账本，恢复前核对状态；不能把有提交记录等同于可安全重做。

**5. 安全。** 每个任务一个独立的沙箱，优先用 microVM，比普通容器隔离更强。代码仓库的凭证不进沙箱，由外部代理在提 PR 时注入。出网默认拒绝，包管理器的源走白名单。仓库里的 issue 内容和代码注释都算不可信输入，读过之后不允许执行对外发送数据的操作。

**6. 评测和观测。** 离线用一批历史上已合并的 PR 做题：给 agent 原始 issue，用原 PR 的测试判卷，同一题跑三次看 pass^3。线上记录每个任务的步数、token、测试是否通过、PR 是否被合入，以及人审时改了多少。改提示词或换模型之前，先跑一遍离线集。

**和 Claude Code、Codex 对比。** 两者的骨架都是这个循环：通用工具、按需检索、压缩、子 agent 隔离上下文、权限分级。差别主要在默认策略上，比如权限默认放多宽、沙箱怎么实现、压缩怎么触发。可以结合[用 Codex 还是 Claude Code](../p1-tools/01-tools-landscape.md)和第 3 部分拆过的细节来讲。

## 示范二：客服助手，怎么知道它在帮忙而不是添乱

这道题的重点在第 1 步和第 6 步，中间几步可以讲得简略。

**澄清「帮忙」怎么定义。** 先问清楚业务指标：一次解决率、转人工率、用户满意度。再问哪些操作有副作用，比如退款、改订单。这些操作要有人工确认，或者设金额上限。

**评测怎么设计。** 这是这道题的核心：

- **离线**：从历史工单里挑出典型问题和失败案例，建一个评测集。每道题按最终状态判分，比如退款是否真的发起、金额对不对，而不是看回复的措辞。同一题跑多次，看 pass^k，因为同一个用户问三次，三次都要答对。
- **评委**：话术质量这类没法用代码判的，用 LLM 评委，每个失败类别配一个只判通过或不通过的评委，并先用人工标注校准，报告它和人工判断的一致率。
- **线上**：抽样跑评委，同时看转人工率和重复来访率。助手在「添乱」时，往往表现为转人工率下降了，但同一个用户隔天又来问同样的问题。
- **闭环**：线上发现的新失败，归类后补进离线评测集。

**添乱的几种典型表现，要提前设计监控**：答非所问，用户重复提问；编造政策，回复里出现知识库里没有的条款；越权操作，调用了不该调用的工具。最后一种不能只靠监控，要用代码闸门挡住。

## 高频追问：怎么看发布会上的榜单分数

系统设计聊到评测时，常被顺带问这个。按这个顺序答：

1. **怎么跑的**：用的什么 harness、跑了几次、报的是 pass@1 还是 pass@k。同一个模型换一套 scaffold，分数可以差很多。
2. **数据靠不靠谱**：有没有污染，是不是已经饱和。典型例子是 OpenAI 在 2026 年 2 月宣布不再报告 SWE-bench Verified，理由是数据有污染、部分测试本身有缺陷，最近半年的最高分只从 74.9% 涨到 80.9% [^swe]。
3. **测的是不是你关心的**：τ²-bench 测工具调用和对话，换成用户也能操作环境的模式后，一些模型的通过率明显下降 [^tau]；BrowseComp 测难找的事实检索；METR 的 time horizon 衡量的是任务难度，不是 AI 花了多长时间 [^metr]。
4. **最后落到自己**：用自己的任务集复测才算数。

## 对照你的环境

- 系统设计第 5 步讲的「凭证不进沙箱」，你可以对照自己的环境想一想：Claude Code 执行命令时，能读到你 shell 里的哪些环境变量？哪些 token 其实不该让它看到？
- 示范一里「项目约定放在仓库根目录的说明文件里，每次预先加载」，就是你每个仓库里的 CLAUDE.md 和 AGENTS.md。

## 回到开头的问题

为什么单项会答却讲不出系统？需要显式连接需求、状态、权限与评测。用六步框架完整讲两遍示范，再换一道题自己讲。

回到主线：系统设计的六步，前四步都在回答「模型这一轮该看到什么、能做什么」，后两步在回答「怎么确认它做对了、做错了能不能兜住」。

## 常见坑

- **系统设计一上来就画架构图。** 先花两三分钟澄清需求，问清有哪些副作用、怎样算做对。跳过这一步，后面的取舍就没有依据。
- **每一步只说做法不说代价。** 面试官会一直追问，直到你说出代价为止。
- **把评测留到最后一句带过。** Agent 岗的系统设计，评测往往是最被看重的部分。
- **只刷题不做项目。** 题库是用来查漏的，项目才是面试的主体。

## 练习

**1.** 用六步框架，自己完整讲一遍「设计一个 Deep Research agent」，录音后对照示范一检查漏了哪一步、哪一步没讲代价。

<details>
<summary>提示</summary>

本章设计题表里「设计多 agent 协作、产出带引用报告的 Deep Research」那一行已经给了骨架：编排者加执行者，子 agent 只回传摘要，最后单独核对引用。

按六步自查最容易漏的地方：第 2 步要说清哪段固定（最后的引用核对、报告格式）、哪段交给模型（搜什么、搜几轮）；第 4 步讲子 agent 隔离上下文时，补上代价（额外调用、摘要信息损失与协调成本），参考 [Agent 核心机制](03-agent-mechanisms.md) 第 7 题和 [Sub Agent](../p1-tools/10-sub-agent.md)；第 6 步讲怎么判卷，比如引用是否真的支持结论。

</details>

**2.** 把 Coding Agent 改成多租户云服务，指出原方案必须改变的三处，并说明如何验证。

<details><summary>提示</summary>

至少检查租户与仓库授权、沙箱/凭证边界、排队和资源配额、任务恢复与外部副作用之一。分别给出失败注入与可观测结果，而不是只在图上多画一个 API Gateway。基础回看[全栈与生产工程](04-production-engineering.md)。

</details>

**3.** 开放题：示范二里「转人工率下降，但同一个用户隔天又来问」这个信号，你还能想到哪些类似的「指标看着变好，其实在变坏」的情况？怎么设计监控发现它们？

<details>
<summary>提示</summary>

判断方向：找「代理指标」和「真实目标」可以被分开的地方，被优化的往往是更容易动的那一个。几个例子：

- 平均对话轮数下降，但用户其实是放弃了；
- 工具调用失败率下降，因为模型不再调用工具，直接编答案；
- LLM 评委打分上升，但和人工标注的一致率在下降（评委被讨好了）；
- 平均 token 下降，因为压缩更激进，长任务的完成率掉了。

监控设计：每个指标配一个「反向指标」成对看（转人工率配重复来访率）；按最终状态判分而不是看措辞；定期抽样人工复核、校准评委。原理在 [Agent 评测实践指南](../p3-agent-internals/14-agent-eval-guide.md) 和 [可观测性](../p2-agent-basics/08-agent-observability.md)。

</details>
